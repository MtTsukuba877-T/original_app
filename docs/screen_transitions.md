## 1. プロジェクト概要

### 1.1 サービスコンセプト

契約企業の従業員等向けのストレスチェックアプリ。**BtoBtoEモデル**で、契約企業(B)が支払い、産業保健スタッフ(B)が運用、従業員(E)がエンドユーザー。

### 1.2 コアバリュー

| 価値 | 内容 | 主な受益者 |
|---|---|---|
| 価値A | 受検しやすさ(PC不要でスマホ受検) | 従業員 |
| 価値B | 通知配信(メール不要で通知到達、LINE経由)等による企業担当者の負担軽減 | 企業担当者 |

### 1.3 MVPの目的

両コアバリューを最小限の機能で検証する設計を志向する。

## 3. ユーザーテーブル構成

| テーブル | 対象ユーザー | 認証方式 |
|---|---|---|
| `users` | システム管理者+企業担当者(roleカラムで区別) | Devise(メール+パスワード) |
| `employees` | 受検者(従業員) | 独自実装(受検者番号+生年月日→変更後パスワード) |

**usersテーブルのrole値（MVP）**:
- `system_admin`: システム管理者
- `company_hr`: 企業担当者（人事担当）

**MVPで採用するDevise機能**:
- `:database_authenticatable`: メール+パスワード認証（必須）
- `:recoverable`: パスワードリセット機能
- `:validatable`: メール・パスワードのバリデーション
- `:invitable`: 招待メール機能（devise_invitable、企業担当者アカウント作成に使用）

**MVPで除外するDevise機能**:
- `:registerable`: 新規登録機能 → 除外（招待メール経由のみで登録するBtoBサービスのため）
- `:rememberable`: Remember me機能 → 除外（個人情報保護、プライバシーマーク取得予定のためセキュリティ優先）

※MVPでは企業担当者（`company_hr`）は受検状況（未受検・受検済み）のみ把握でき、受検結果の内容は閲覧できません。

※本リリース版では`users`を`admin_users`/`company_users`に別テーブル化予定。本リリース版の`company_users`テーブルでは以下の3役割で管理する：
- `company_admin`: 実施者（法令上の実施責任者、受検結果閲覧可）
- `company_admin_staff`: 実施事務従事者（実施者の補助、受検結果閲覧可）
- `company_hr`: 企業担当者（受検状況のみ閲覧可、受検結果は非開示）

## 5. 受検者フロー詳細

### 5.1 フェーズ1: 事前登録期間(受検期間開始前)

```
[企業担当者配布の企業別QRコード]
        ↓ (スマホで読み取り)
[LINE友だち追加]
        ↓ (Webhookで企業ID+LINEユーザーIDをDB保存)
[LINEメッセージ受信: 初期登録案内]
   ※トークン付きURL
        ↓ (URLタップ)
[E-1 初期登録画面]
   ※受検者番号+生年月日入力
   ├─ 名簿照合失敗 → 同画面にエラー表示(リトライ制限なし)
   └─ 名簿照合成功 ↓
[E-2 初期登録完了画面]
   ※「初期登録完了。受検開始日をお待ちください。
       お疲れさまでした。ブラウザを閉じてください。」
        ↓ (ブラウザを閉じる)

   ===== 受検期間開始まで待機 =====
```

### 5.2 フェーズ2: 受検期間中

```
[企業担当者が「受検案内一斉配信」ボタン押下]
        ↓
[LINEメッセージ受信: 受検案内]
   ※ログイン画面へのURL
        ↓ (URLタップ)
[E-3 ログイン画面]
   ※受検者番号+パスワード入力
   ├─ 認証失敗 → 同画面にエラー表示
   └─ 認証成功 ↓
       状態で分岐
       │
       ├─ 初回ログイン → [E-4 強制パスワード変更画面]
       │       ※新パスワード+確認用パスワードの2つ
       │       ※要件:半角英数字混在8文字以上
       │       ↓ (変更完了)
       │
       ├─ パスワード変更済、未受検 → [E-5a～E-5d 受検画面]
       │       ※冒頭に注意事項箇条書き、57問4択
       │       ※ログアウトボタン(確認ポップアップ付き)
       │       ├─ 未回答あり → 同画面にエラー表示
       │       ├─ ログアウト → 確認ポップアップ
       │       │       ※「受検途中でログアウトすると回答は保存されず、
       │       │           最初からやり直しになります。よろしいでしょうか。」
       │       │       └─ はい → [E-3 ログイン画面]
       │       └─ 全問回答完了 → [E-6・E-6' 結果表示画面]
       │              ↓ (ログアウト)
       │           [E-3 ログイン画面]
       │
       └─ 受検済 → [E-6・E-6' 結果表示画面]に直接遷移
                       ↓ (ログアウト)
                    [E-3 ログイン画面]
```

### 5.3 受検者フローの主な仕様

| 項目 | 仕様 |
|---|---|
| 初期パスワード | 受検者の生年月日(YYYYMMDD) |
| パスワード要件 | 半角英数字混在8文字以上 |
| 初回ログイン時の挙動 | E-4強制パスワード変更画面に遷移 |
| 受検画面の注意事項 | 冒頭に箇条書き表示(無回答不可、ログアウトで回答消失等) |
| ログアウト時の挙動 | 受検中の回答は破棄(MVPでは途中保存なし) |
| 受検済者の再ログイン | E-6・E-6'結果表示画面に直接遷移 |
| パスワード忘失対応 | MVPでは運用対応(企業担当者経由でシステム管理者に連絡→DB直接操作) |
| 受検画面のアクセス制限 | 受検期間中のみアクセス可能 |
| 結果表示画面の閲覧 | 受検期間後も閲覧可能(PDF保存等のため) |

### 7.3 主な仕様

| 項目 | 仕様 |
|---|---|
| 企業ID | Railsデフォルト連番(5桁ゼロパディング表示なし) |
| 企業の削除機能 | MVPでは実装しない(編集のみ) |
| 受検期間のデータ構造 | **MVPから実施回テーブル(`stress_check_periods`)で管理**。MVPは1企業1レコードで運用。 |
| 受検期間の粒度 | 日付のみ(時刻なし) |
| 判定方法 | `stress_check_periods.judgment_method`カラムで管理。MVPは`simple_sum`（単純合計法）固定。本リリース版で`raw_score_conversion`（粗点換算表）を追加予定。 |
| 本リリース版での発展 | 1企業複数実施回対応、企業IDをUUID化、判定方法のUI選択機能 |

**実施回テーブルをMVPから新設する根拠**:
労働安全衛生法第66条の10により、常時50人以上の労働者を使用する事業者はストレスチェックの年1回実施が義務付けられている。
また、実施結果は5年間の保存義務がある。1企業につき毎年1回、確実に実施回が発生し、過去実施回データも保存対象となるため、
テーブル構造としてMVPから実施回テーブルを準備しておく。

**判定方法を実施回テーブルに配置する根拠**:
各企業の各実施回ごとに判定方法（単純合計法・粗点換算表）を設定するため。判定方法は業務データとして重要（法令・監査対応）で、
プライバシーマーク取得予定を踏まえ、DBに明示的に記録する。同一実施回内では判定方法は一意であり、実施回の属性として扱うのが自然。

#### 【カテゴリー①】カラム設計工程で保留した項目

- **受検者一覧DL機能の進捗情報取得方法**：動的計算（アプローチA） / 状態カラム（アプローチB） / ビュー・集計テーブル（アプローチC）

  - 本リリース版（仮）：`employees`に`stress_check_period_id`を追加、実施回ごとに別レコード

  - 過去実施回時点のスナップショット保持（産業保健の法令要件・監査対応）
  - 本リリース版開発着手時に、以下を含めて再検討：
    - MVPでの実装経験を踏まえた判断
    - 過去実施回データのイミュータブル性の確保
    - 年次比較レーダーチャートの実装方法（同一人物判定は`(company_id, examinee_number)`）

- **`users`テーブルと`stress_check_periods`（実施回）の関連の見直し**
  - MVP：`users`は`company_id`のみで企業に紐付け、実施回との直接関連なし

    - 実施回ごとの企業担当者履歴管理

    - 各役割の権限管理の詳細化（Pundit連携）
  - 本リリース版開発着手時に、`employees`テーブル設計方針とセットで再検討

- **`sections`テーブルのバリデーション強化**
  - MVP：外部入力がないため、`code`の値制限バリデーションは不要
  - 本リリース版：以下を検討

  - MVP：外部入力がないため、`answer_number`の数値制約バリデーションは不要
  - 本リリース版：以下を検討
    - `answer_number`の数値範囲バリデーション（1〜4の整数）
    - マスタメンテナンス画面の実装可否

- **`judgments`テーブルのバリデーション強化**

  - 本リリース版：実施回ごとの再登録が必要かの実務検証

## 10. 設計上の重要な原則(議論を通じて確認された事項)

### 10.1 MVPスコープ規律

- 実装工数・運用現実性を根拠に機能を本リリース版に先送り
- その理由を明示的に記録する姿勢を一貫して保つ

### 10.2 コアバリューへの照合

- 設計判断は常にコアバリュー①(受検しやすさ)・②(通知配信等による企業担当者の負担軽減)への貢献度で検証

### 10.3 単一責任の原則

- 1つのカラム(役割)に複数の責任を持たせない設計を本リリース版で意識
- MVPではシンプルさを優先

### 10.4 段階的発展

- MVPでシンプルに実装→本リリース版で本格化、という段階的な発展を意識

### 10.5 第3正規化までの徹底（カラム設計工程で確認）

- カリキュラム基準①「同じ意味のデータを何度も持たない」に厳密に準拠
- 横並び構造（`answer_1`〜`answer_57`など）を避け、正規化された縦持ちレコードで管理
- 「1つの原子的な情報＝1レコード」の原則を全テーブルで適用

### 10.6 enum vs マスタテーブルの使い分け

- **enum向き**：付随情報が少なく、業務データとして独立して扱わない選択肢（例：`users.role`、`employees.sex`、`stress_check_periods.judgment_method`）
- **マスタテーブル向き**：付随情報が多く、業務データとして独立して扱う選択肢（例：`sections`）
- 判断基準：「そのカラムを、独立したテーブルとして管理する価値があるか？」

### 10.7 enum値の開始番号ポリシー（案C：使い分け方式）

- **CSV等の外部入力があるカラム**：1から始める（Excelでの空欄との区別のため）
  - 例：`employees.sex`（1: 男性、2: 女性）
- **コード内でセットする内部データ**：0から始める（Railsの慣習に従う）
  - 例：`users.role`、`stress_check_periods.judgment_method`
- Railsの規約「Convention over Configuration」を尊重しつつ、必要な例外を明確化

### 10.8 業務ロジックとDB制約の分離

- **DB制約**：`NOT NULL`、`UNIQUE`、外部キー制約など、DB層で強制すべきデータ整合性
- **Railsバリデーション**：条件付き必須、値の範囲チェック、複雑な業務ロジックなど
- 例：`stress_check_periods`の`start_date`/`end_date`は「両方入力または両方未入力」の業務ロジックをRailsバリデーションで実装

### 10.9 認可制御とDB設計の分離

- **DB層**：役割情報の保存（`users.role`）
- **モデル層**：役割判定メソッド（Railsのenum自動生成）
- **認可層**：Punditポリシーで権限判定
- DB設計と認可制御は独立した設計判断として扱う

### 10.10 マスタデータとトランザクションデータの区別（リレーションシップ整理工程で確認）

- **マスタデータ**：時点に依存しない情報（`companies`、`users`、`employees`、`line_friends`、`sections`、`answer_options`、`questions`）
- **トランザクションデータ**：時点に依存する情報（`stress_check_responses`、`judgments`、`results`）
- マスタは実施回との直接関連なし、トランザクションは実施回との直接関連あり
- 関連を辿る時は、トランザクションテーブル経由で判定（例：`period.stress_check_responses.map(&:employee)`）

### 10.11 バリデーションポリシー（リレーションシップ整理工程で確立）

- **外部入力があるカラム**：バリデーション厚めに設定（悪意ある入力への防御）
  - 例：`stress_check_responses.raw_answer`（1〜4の整数チェック）
- **外部入力がないマスタデータ**：MVPではバリデーション最小限（seedsで管理）
  - 例：`sections`、`answer_options`
- **業務の根幹に関わる情報**：外部入力がなくてもバリデーション厚めに設定
  - 例：`questions.reversed`（boolean厳密チェック）、`judgments.section_score`（0以上の整数）
- 判断基準：「そのカラムが不正な値になった時、業務にどれだけ影響するか」

### 10.12 `has_many`/`belongs_to`の判定ルール（リレーションシップ整理工程で確認）

- 外部キー（`〜_id`カラム）を持つ側：`belongs_to`
- 外部キーを持たない側：`has_many`または`has_one`
- 判定方法：「そのテーブルに相手のIDを持つカラムはあるか？」
- 1対1でも実装レベルでは非対称（外部キーは片方だけ）

### 10.13 `dependent`オプションの統一方針（リレーションシップ整理工程で確認）

- 全テーブルで`dependent: :restrict_with_error`を採用
- MVPでは削除機能を実装しない前提
- 万一の誤削除を防ぐ「保険」として設定
- 5年間の保存義務（労働安全衛生法）に準拠
